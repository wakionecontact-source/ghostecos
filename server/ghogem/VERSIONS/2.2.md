## Основное направление
- Оценка моделей, сравнение моделей и GhoGem Arena.
- Версия 2.2 должна собрать реальные данные о качестве, скорости, стабильности и специализации моделей, чтобы подготовить фундамент для автоматического выбора моделей и режима Work в GhoGem 3.0.

## Confirmed
- GhoGem Arena: слепое сравнение ответов моделей на одинаковый запрос.
- Система оценок/статистики моделей.
- Результаты 2.2 должны быть пригодны как данные для будущего model router в 3.0.

## Arena — базовая идея
- Пользователь отправляет один запрос, две модели получают одинаковую задачу.
- Названия моделей скрыты до голосования, чтобы уменьшить брендовый bias.
- Порядок ответов A/B рандомизируется.
- После выбора модели раскрываются.
- Голос сохраняется как head-to-head результат между конкретными моделями.

## Что измерять
- Победы/поражения/ничьи в Arena.
- Скорость ответа и time-to-first-token.
- Ошибки провайдера и долю успешных запросов.
- Tool-call success/failure, если сравнение допускает tools.
- Размер входа/выхода и context-limit ошибки.
- Категорию запроса: код, разговор, reasoning, большой контекст, изображения, web, tools и другие.

## Важно для 3.0
- Нужны отдельные показатели по категориям, а не только один общий рейтинг модели.
- Производительность endpoint/provider нужно отличать от качества самой модели: одна и та же модель у двух провайдеров может иметь разную скорость и стабильность.
- Данные должны храниться по конкретной версии/model id, чтобы обновление модели не смешивалось со старой статистикой.

## Rating structure — confirmed
- У каждой модели есть общий рейтинг и отдельные рейтинги по категориям.
- Общий рейтинг отражает качество модели в целом и считается отдельно от категорийных рейтингов.
- Категорийные рейтинги ведутся независимо друг от друга: код, reasoning, обычный разговор, vision, tools, web, скорость, большой контекст и другие утверждённые категории.
- Модель может занимать высокое место в общем рейтинге и при этом иметь существенно другое место в конкретной категории.
- Общий рейтинг не должен быть простым средним мест по категориям; он опирается на общие результаты сравнений/оценок модели.

## Category assignment — confirmed
- Категорию Arena/оценки может выбрать пользователь вручную.
- GhoGem автоматически проверяет выбранную категорию по содержанию запроса.
- Если пользователь не выбрал категорию, GhoGem определяет её сам.
- Пользовательский выбор не считается абсолютным: явно неподходящая категория должна быть отклонена или исправлена системой, чтобы не загрязнять статистику рейтинга.

## Arena pair selection — confirmed
- На текущем этапе пары моделей в Arena выбираются случайно из доступных и подходящих под запрос/категорию моделей.
- Умный подбор соперников по рейтингу или ручной выбор пары можно рассмотреть позже, но в первой версии Arena это не требуется.

## Arena reveal flow — confirmed
- До голосования пользователю показываются только анонимные `Модель A` и `Модель B`.
- Названия моделей не раскрываются до того, как пользователь проголосует.
- Голосование обязательно для раскрытия конкретных моделей в этом бою.
- После голоса показываются реальные названия обеих моделей и сохраняется результат сравнения.

## Arena vote options — confirmed
- Варианты голосования: `A лучше`, `B лучше`, `Одинаково`, `Оба плохие`.
- Любой из этих четырёх вариантов считается завершённым голосованием и после него раскрываются реальные модели.

## Rating source — confirmed
- Публичный рейтинг моделей строится именно на голосованиях пользователей в Arena.
- Техническая телеметрия (скорость, ошибки API, tool-call success, context overflow и т.п.) хранится отдельно и не должна напрямую менять пользовательский рейтинг модели.
- Общий и категорийные рейтинги используют результаты пользовательских голосований как основной источник данных.

## Arena negative vote — confirmed
- Голос `Оба плохие` является отрицательным сигналом для обеих моделей и понижает рейтинг обеих.

## Arena tie vote — confirmed
- Голос `Одинаково` даёт обеим моделям небольшой положительный прирост рейтинга, меньший, чем победа в паре.

## Rating fairness / normalization — confirmed
- Главный приоритет рейтинга — максимально честная относительная расстановка моделей по пользовательским голосованиям, а не фиксированная красивая шкала.
- Внутренний рейтинг не должен иметь жёсткого потолка, который способен исказить разницу между сильными моделями.
- Если публичная шкала имеет верхнюю границу (например 1000), она нормализуется глобальным сдвигом: при приближении лидера к потолку одинаковое число поинтов вычитается у всех моделей.
- Глобальный одинаковый сдвиг не меняет порядок моделей и разницы между их внутренними рейтингами.
- Новые модели должны иметь более высокую неопределённость/подвижность рейтинга; по мере накопления сравнений рейтинг стабилизируется.
- Рейтинг должен хранить не только score, но и показатель уверенности/объёма данных, чтобы малое число голосов не воспринималось как столь же надёжное, как тысячи сравнений.
- Общий и категорийные рейтинги используют одну и ту же логику честной относительной расстановки, но считаются независимо.

## Universal image generation — confirmed
- Нужен не узкий генератор карточек, а универсальный генератор изображений кодом.
- Один движок должен уметь создавать произвольные изображения: карточки моделей, рейтинги, Arena-результаты, QR-коды, обложки версий, постеры, схемы, таблицы, инфографику и другие визуалы.
- Карточки являются только одним из шаблонов/сценариев поверх общего image renderer.
- Базовый рендеринг предпочтительно строить через HTML/CSS/SVG с экспортом результата в PNG.
- В дальнейшем генератор должен быть доступен как tool для ИИ: модель формирует структуру/код изображения, сервер безопасно рендерит его и отправляет PNG пользователю в Telegram.
- Рендеринг должен выполняться в изолированной среде без произвольного доступа HTML/JS к системе и сети.

## Reliability fixes during 2.2 development
- Добавлено полноценное отключение напоминаний: `disable_reminder` полностью отменяет будущие срабатывания и больше не путается с `skip_next_reminder`.
- Явные фразы `отключи/выключи/выруби/убери напоминание` обрабатываются детерминированно без зависимости от LLM; предмет напоминания сопоставляется безопасно, без подстановки другого активного задания.
- Запрос `пропусти ближайшее` по-прежнему пропускает только одно срабатывание.
- 429, provider 5xx и hard timeout больше не повторяются тем же неизменённым запросом перед failover.
- Для SambaNova в основном agent loop установлен более короткий step timeout 35 секунд; для остальных 60 секунд.
- Повторные пустые ответы ограничены: один повтор, затем fallback вместо бесконечного цикла.

## Context Splitter — implemented
- Большие пользовательские prompts больше не обрезаются до 1500 символов: они автоматически делятся на части и последовательно сворачиваются в рабочий контекст.
- Деление сохраняет все исходные символы между chunk'ами; границы выбираются по абзацам/строкам/словам без удаления текста.
- Сжатие сохраняет требования, ограничения, имена, числа, даты, URL, идентификаторы и существенные детали кода; начало и конец исходного запроса дополнительно передаются дословно.
- Исходный полный prompt сохраняется в локальной истории; provider-facing summary является временным и в историю не записывается.
- Есть proactive split по бюджету выбранной модели и reactive split после реального `context length` / HTTP 413 ответа провайдера.
- Бюджет можно задавать на уровне конкретной модели через `context_chars`; без него используются provider defaults.
- Для малоконтекстных моделей включается компактный system-core: обязательные safety/permissions/identity/time/reminder rules остаются, подробные tool-инструкции подгружаются через `get_tool_instructions` по требованию.
- На Groq system в тесте уменьшен примерно с 15.5k до 10.5k символов при рабочем бюджете 12k.
- Splitter подключён к основному `ask_ai`, legacy `ask_ai_stream` и Web agent loop.
- Добавлен regression-test `test_context_splitter.py`.

## Context Splitter / prompt chunking — implemented during 2.2 development
- Большие пользовательские запросы больше не обрезаются до 1500 символов при переполнении контекста модели.
- Для малоконтекстных моделей GhoGem заранее делит исходный prompt на части, последовательно сворачивает их в рабочие заметки и только затем выполняет основной запрос.
- Splitter сохраняет требования, ограничения, имена, числа, даты, URL, идентификаторы, важные цитаты и существенные детали кода; начало и конец исходного запроса дополнительно передаются дословно.
- Исходный пользовательский prompt сохраняется в локальной истории полностью; сжатое представление используется только для provider-facing вызова.
- Если провайдер сам возвращает context-length/too-many-tokens/413, GhoGem один раз принудительно перепаковывает исходный prompt для конкретной модели и повторяет запрос вместо немедленного fallback/ошибки.
- Для Groq и других малоконтекстных маршрутов длинный system prompt автоматически заменяется компактным system-core: критические правила, безопасность, идентичность, время, права и reminder-семантика сохраняются, а подробные инструкции tools подгружаются через get_tool_instructions по требованию.
- В agent loop старая история может быть отброшена при переполнении, но текущий пользовательский prompt больше не режется молча.
- Та же логика подключена к Telegram ask_ai, streaming path и Web agent.
- Добавлен regression test test_context_splitter.py, проверяющий отсутствие потери символов при разбиении, сжатие большого prompt и распознавание context-limit ошибок.

## Interactive user choice / ask_user_choice — implemented
- Добавлен универсальный AI-tool `ask_user_choice` для интерактивного уточнения пользователя прямо в Telegram.
- ИИ передаёт один `question` и 2–8 `options`; интерфейс сам нумерует варианты и автоматически добавляет кнопку `✍️ Написать свой ответ`.
- Карточка оформлена стабильно: сверху всегда остаются вопрос и все варианты, при взаимодействии меняется только нижняя строка состояния (`выбери`, `напиши свой ответ`, `выбран вариант`, `свой ответ отправлен`).
- Inline-кнопки: `1️⃣ Вариант 1`, `2️⃣ Вариант 2`, ... и `✍️ Написать свой ответ`.
- Нажатие готового варианта продолжает тот же AI-chat с фактическим ответом пользователя; собственный текст после кнопки `Написать свой ответ` работает так же.
- `ask_user_choice` является terminal interaction: после успешного показа вопроса текущий agent-run немедленно останавливается и не может сам придумать/выбрать ответ пользователя.
- Если модель прислала несколько tool calls одновременно, все вызовы после успешного `ask_user_choice` не выполняются до ответа пользователя.
- Интерактивный выбор не является подтверждением удаления, оплаты, изменения разрешений или других защищённых/разрушительных действий; для них остаются отдельные серверные подтверждения.
- Состояние вопросов хранится в `interactive_choices.db`, привязано к owner user_id + Telegram chat + message_id + AI chat, переживает рестарт бота и имеет TTL.
- Защита от двойного клика, чужого пользователя, устаревшей/подменённой карточки и старого message_id.
- Новый вопрос пользователя делает предыдущий активный интерактивный вопрос устаревшим; старые записи периодически очищаются.
- Web/background/scheduled agents не получают `ask_user_choice`: инструмент доступен только там, где есть доверенный Telegram callback UI.
- Подробная lazy-инструкция добавлена в `tool_registry.py`: когда применять, структура вариантов, запрет на собственную нумерацию/`Другое`, обязательная остановка после вызова и границы безопасности.
- Добавлен regression suite `test_interactive_choices.py`: persistence, owner binding, custom mode, UI invariants, lazy tool instructions, terminal behavior, Telegram callback flow и continuation в исходный AI-chat.

## Interactive user choice — implemented
- Добавлен Telegram-only tool `ask_user_choice`: ИИ может остановить агентный проход и показать пользователю интерактивный вопрос с 2–8 вариантами и отдельной кнопкой `✍️ Написать свой ответ`.
- Карточка отображает `❓ Вопрос`, затем `1️⃣ Вариант 1`, `2️⃣ Вариант 2` и т.д.; нижняя строка состояния меняется без изменения вопроса и вариантов.
- В обычном состоянии footer: `👇 Выбери один из вариантов ответа снизу`; после выбора своего ответа: `✍️ Напиши свой ответ следующим сообщением — вопрос и варианты останутся перед тобой.`
- После нажатия варианта карточка фиксирует выбранный номер, убирает кнопки и реальный выбор возвращается в тот же AI chat как следующий пользовательский контекст.
- При `Написать свой ответ` следующий текст пользователя относится к открытому вопросу, карточка отмечает отправку ответа, затем исходная задача продолжается в том же AI chat.
- Вопросы хранятся в SQLite (`interactive_choices.db`), привязаны к user_id, Telegram chat, message_id и AI chat; токены одноразовые, имеют TTL, старый открытый вопрос supersede-ится новым.
- Чужой пользователь, другая карточка или устаревший token не могут отправить выбор.
- `ask_user_choice` является terminal interaction: после успешного показа модель не может сама придумать выбор и продолжить ответ до реального пользовательского действия.
- Интерактивный выбор не является подтверждением удаления, платежа, изменения разрешений, очистки данных или другого защищённого действия; такие операции требуют собственного серверного подтверждения.
- Tool не доступен background/scheduled задачам и не рекламируется Web/GhoSou агентам; там нужно задавать обычный текстовый вопрос.
- Подробная lazy-инструкция через `get_tool_instructions` объясняет, когда использовать choice UI, как формировать question/options, не добавлять нумерацию/`Другое`, не задавать несколько независимых вопросов одним вызовом и обязательно остановиться после показа.
- Добавлен regression test `test_interactive_choices.py`: persistence, UI stability, owner binding, custom answer, exact chat resume, terminal agent behavior и safety boundary.

## Interactive answer choice — implemented during 2.2 development
- Добавлен Telegram tool `ask_user_choice` для случаев, когда ИИ реально нужен выбор пользователя из 2–8 вариантов.
- Карточка сохраняет вопрос и все варианты перед глазами; после действия меняется только нижний статус.
- Формат карточки: `❓ Вопрос`, затем нумерованные `1️⃣ Вариант 1`, `2️⃣ Вариант 2` и т.д.; снизу статус `👇 Выбери один из вариантов ответа снизу`.
- Inline-кнопки: `1️⃣ Вариант 1`, `2️⃣ Вариант 2`, … и отдельная `✍️ Написать свой ответ`.
- После `Написать свой ответ` вопрос/варианты не исчезают; footer меняется на просьбу написать текст следующим сообщением.
- Нажатие варианта или собственный текст возобновляет именно тот AI-чат, который задал вопрос, с реальным ответом пользователя.
- После показа карточки текущий agent turn останавливается и не имеет права выбирать за пользователя или продолжать финальный ответ.
- Карточки persistent и owner-bound; чужой Telegram user не может ответить на чужой вопрос; новая карточка безопасно заменяет старую активную.
- `ask_user_choice` запрещён в фоновых scheduled tasks и не считается подтверждением удаления, платежа, изменения разрешений или другого защищённого/разрушительного действия.
- В `tool_registry.py` добавлена подробная lazy-инструкция: когда использовать выбор, как строить options, запрет дублировать кнопку `Свой вариант`, правило одного вопроса за вызов и обязательная остановка до ответа.
- Добавлен `test_interactive_choices.py`; тесты persistent store, UI, callbacks, custom answer, owner isolation, handshake и terminal agent behavior проходят.

- Пока пользователь выбирает, основной agent-turn остаётся живым и показывает `⏳ … ждёт ответа…`; Telegram typing на время ожидания выключается.
- Нажатие варианта или ввод собственного текста будит ТОТ ЖЕ `process_request` через owner-bound Future: сохраняются модель, AI-chat, status-message и вся предыдущая хронология действий.
- После ответа в `Ход работы` добавляется фактический выбор пользователя, после чего агент продолжает исходную задачу.
- Если бот был перезапущен и live Future потерян, persistent SQLite-карточка безопасно продолжает точный AI-chat новым проходом.
- Вопросы owner-bound, одноразовые, имеют TTL; чужой пользователь не может проголосовать за владельца.

- Утечки `[BLOCK: ANSWER]`, `[BLOCK: THOUGHT]`, `[BLOCK: ACTION]` и их частично пришедших streaming-маркеров скрываются из preview и финального Telegram-ответа.

## Interactive choice reliability fix
- Короткие команды `сделай выбор`, `покажи выбор`, `дай выбор` теперь сами по себе считаются явным запросом на Telegram interactive choice; слова `варианты/ответы` больше не обязательны.
- Команды вида `сделай выбор за меня` / `выбери сам` не перехватываются интерактивным UI: это обычная просьба ИИ принять решение.
- Если provider несколько раз описывает намерение показать выбор, но не отдаёт настоящий function/tool call, GhoGem больше не заканчивает ответ ошибкой `Модель сообщила о действии...`.
- После исчерпания обычных tool-call retries включается server-side recovery: отдельный tool-less JSON-проход формирует и валидирует `question + options`, после чего доверенный Telegram callback показывает настоящую карточку.
- Recovery использует недавний диалог и незавершённый текст модели, поэтому короткое `сделай выбор` может продолжить ближайший открытый вопрос из контекста.
- Recovery не исполняет выбранное действие и не заменяет защищённые подтверждения; он только создаёт UI вопроса.
- Добавлен `test_choice_recovery.py`: короткий trigger, choose-for-me exclusion, JSON recovery и end-to-end сценарий repeated no-tool progress -> real interactive card.
- После исправления проходят `test_choice_recovery.py`, `test_interactive_choices.py` и полный `test_ghosou_tools.py`.

## Stop UX + provider limit routing — implemented
- При ручной остановке генерации Telegram-карточка больше не затирает накопленный `Ход работы`: уже выполненные/завершённые шаги остаются в том же сообщении, снизу добавляется статус `Генерация остановлена пользователем`.
- Добавлен regression-тест Stop flow: финальная остановленная карточка обязана сохранять `Ход работы` и выполненные шаги.
- Внутренние GhoGem-лимиты RPM/RPD не менялись: диагностика показала, что проблемные ограничения приходили от внешних API-провайдеров, а не от внутренней очереди.
- После HTTP 429 конкретная модель получает runtime cooldown 180 секунд, а весь провайдер — 75 секунд; automatic fallback временно исключает эти маршруты и не перескакивает на другую модель того же уже исчерпанного API.
- Модель, зависшая по hard timeout, получает отдельный model-only cooldown 90 секунд, не блокируя остальные модели провайдера.
- Groq 429 перед переключением на резервный ключ также отмечает исчерпанный route, чтобы последующие запросы не наступали на тот же лимит.
- Runtime cooldowns хранятся только в памяти процесса и автоматически истекают; рестарт сервиса не сохраняет устаревшие ограничения.

## Modular system prompt / context budget — implemented 2026-10-02
- Старый монолитный `SYSTEM_PROMPT` (~6.6k символов сам по себе, ~14–15.5k после постоянных добавок) больше не отправляется провайдерам в обычном Telegram agent, Web/GhoSou agent и legacy streaming path.
- Добавлен `build_modular_system_prompt`: небольшой постоянный core (идентичность GhoGem, trust/safety, agent handshake, время, текущая модель, краткий tier) + тематические модули только по смыслу текущего запроса.
- Тематические модули сейчас включают GhostEcos, files/media, web, reminders, GhoSou/music+sounds, roleplay, conversation continuity, required attachment, forced web, scheduled-task restrictions и ограниченный UI/tutorial context.
- Детальные правила tools остаются lazy: `get_tool_instructions` подгружает их только перед реальным использованием конкретного tool.
- `tool_registry.PROTOCOL_PROMPT` сокращён примерно с 737 до ~309 символов без изменения server-side handshake/authorization.
- Фактический provider-facing system после protocol: обычный запрос ~2.7–2.9k символов, files/web/reminders обычно ~2.8–3.1k, GhoSou/music ~3.2k вместо прежних ~15.5k.
- Горячая смена модели внутри того же turn теперь тоже пересобирает тот же modular prompt; старый монолит не возвращается после `switch_model`.
- Tutorial state больше не добавляется на каждый turn: UI/tutorial context подключается только для запросов о помощи, меню, настройках, интерфейсе и возможностях.
- Исправлены ложные semantic triggers: школьное `задание` не включает reminder-модуль; обычное `сейчас`/`сегодня` не включает web-модуль само по себе.
- Память и список файлов вынесены из trusted system prompt в низкоприоритетный user-context. В GhoSou namespace они не подмешиваются вообще.
- `seed_history` больше не сохраняет большой system prompt в новый history.json; trusted system собирается динамически на каждом model turn.
- Context Splitter остаётся вторым уровнем защиты: если даже модульный prompt + запрос не помещаются, пользовательский ввод делится/сжимается без молчаливой обрезки середины.
- Добавлен `test_modular_system_prompt.py`; после рефакторинга проходят modular prompt, context splitter, tool handshake, interactive choices, choice recovery, GhoSou tools, model switch, tutorial и inline streaming regression suites.
