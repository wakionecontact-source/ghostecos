GhostChat — Полная схема сигналов
==================================

1. РЕГИСТРАЦИЯ
--------------
Клиент                      Сервер
    |──── POST /api/register ─>|  username, password, pub_keys
    |                          | создаёт аккаунт в БД
    |                          | регистрирует устройство как creator
    |<─── {token, jwt} ────────|
    | сохраняет токен локально |


2. ВХОД (первое устройство / уже зарегистрированное)
-----------------------------------------------------
Клиент                      Сервер
    |── POST /api/login ───────>|  username, password, device_id, device_name
    |                          | проверяет пароль
    |                          | device уже в БД → обновляет last_seen
    |<─── {token} ─────────────|
    | подключается к WS        |


3. ВХОД С НОВОГО УСТРОЙСТВА (требует одобрения)
-----------------------------------------------
Клиент 2 (новый)            Сервер                    Клиент 1 (доверенный)
    |── POST /api/login ───────>|  device_id незнакомый
    |                          | создаёт pending_login запрос
    |<─── {request_id,         |──── login_request ──────>|  device_name, ip
    |      status: pending} ───|                          | показывает уведомление
    |                          |                          |
    | поллит каждые 2с:        |                          | пользователь одобряет
    | GET /api/login_request/  |<── POST approve ─────────|
    |     {request_id}         | генерирует код           |
    |                          |──── login_code ──────────>|  показывает код К1
    |                          |                          |
    | пользователь вводит код  |                          |
    |── POST code_verify ─────>|  проверяет код
    |                          | регистрирует device
    |<─── {token} ─────────────|
    | подключается к WS        |


4. WS ПОДКЛЮЧЕНИЕ / СТАРТОВАЯ СИНХРОНИЗАЦИЯ
--------------------------------------------
Клиент                      Сервер
    |──── WS connect ──────────>|
    |──── {type: auth,          |
    |      token, device_id} ──>|  верифицирует JWT
    |                          | достаёт офлайн-сообщения → шлёт все
    |<─── relay_message[1..N] ─|
    |                          | достаёт trust этого устройства
    |<─── {type: device_trust} |
    |                          | достаёт историю support-чата
    |<─── {type: support_history}
    |                          | достаёт pending login-запросы
    |<─── {type: pending_logins_sync}
    |                          | уведомляет контакты что онлайн
    |                          |──── peer_online ─────────> (все онлайн-контакты)


5. СООБЩЕНИЯ — нормальная доставка
------------------------------------
Клиент 1                    Сервер                    Клиент 2
    |──── relay_message ──────>|                          |
    |                          | сохраняет копию в БД     |
    |<─── msg_saved ───────────|  (статус: stored)        |
    |  (иконка: часики/серый)  |                          |
    |                          |──── relay_message ──────>|
    |                          |                          | сохраняет локально
    |                          |<─── msg_ack ─────────────|
    |                          | удаляет копию из БД      |
    |<─── delivered ───────────|                          |
    | (иконка: ✓ одна галка)  |                          |

    Прочитано:
    Клиент 2 открыл чат ──> relay_seen ──> Сервер ──> seen ──> Клиент 1 (✓✓)

5a. СООБЩЕНИЯ — К2 не ответил за 10 секунд
--------------------------------------------
Клиент 1                    Сервер                    Клиент 2
    |──── relay_message ──────>|                    (офлайн/нет ответа)
    |<─── msg_saved ───────────|                          |
    |                          |──── relay_message ──────>|  (нет ответа)
    |                          |      10 секунд...        |
    |<─── msg_stored ──────────|  (копия остаётся)        |
    | (иконка: 💾 красная      |                          |
    |   дискета = на сервере)  |                          |

5b. СООБЩЕНИЯ — К2 заходит в сеть
------------------------------------
Клиент 1                    Сервер                    Клиент 2
    |                          |<─── ws_connect ──────────|
    |                          | ищет все сохранённые     |
    |                          | сообщения для К2         |
    |                          |──── relay_message[1..N] >|
    |                          |<─── msg_ack[1..N] ───────|
    |                          | удаляет копии из БД      |
    |<─── delivered[1..N] ─────|                          |
    | (иконки: ✓ одна галка)  |                          |
    |<─── peer_online ─────────|                          |
    | К1 проверяет все 💾      |                          |
    | сообщения к К2           |                          |
    |──── relay_message[X..Y] >|  → обычная схема         |

5c. СООБЩЕНИЯ — 1 час истёк, не доставлено
--------------------------------------------
Клиент 1                    Сервер
    |                          |  (таймер 1 час сработал)
    |                          | удаляет копию из БД
    |<─── msg_expired ─────────|
    | (иконка: ✗ крестик)      |
    | сообщение опускается вниз|
    | контекстное меню:        |
    |   [Копировать] [Повторить]

5d. СТАТУСЫ СООБЩЕНИЯ
----------------------
  ○  серый круг    — отправляется (до подтверждения от сервера)
  💾 красная дискета — на сервере (К2 не ответил >10с)
  ✓  одна галка   — доставлено (К2 принял)
  ✓✓ две галки    — прочитано (К2 открыл чат)
  ✗  крестик      — не доставлено (1 час истёк)


6. ФАЙЛЫ
---------
Клиент 1                    Сервер                    Клиент 2
    |── POST /api/upload ──────>|  multipart, зашифрованный
    |                          | сохраняет файл
    |<─── {file_id} ───────────|
    |── relay_message ─────────>|  {type:file, file_id, meta}
    |                          |──── relay_message ──────>|
    |                          |                          | GET /api/file/{file_id}
    |                          |<─────────────────────────|
    |                          |──── файл ───────────────>|
    |                          |<─── file_ack ────────────|
    |                          | (файл остаётся на сервере X часов)
    |<─── delivered ───────────|


7. ПИНГ / ПОНГ (keep-alive)
-----------------------------
Клиент                      Сервер
    |──── {type: ping} ────────>|  каждые 5с
    |<─── {type: pong} ─────────|

    нет pong за 8с  → клиент закрывает WS и переподключается
    нет ping за 30с → сервер закрывает соединение


8. КОНТАКТЫ
-----------
  Добавление:
  Клиент 1 ── POST /api/contacts/add ──> Сервер
  Клиент 1 ── relay_message {type:contact_request} ──> Сервер ──> Клиент 2
  Клиент 2 принимает: relay_message {type:contact_accept} ──> Сервер ──> Клиент 1
  Оба получают pub_keys друг друга

  Удаление:
  Клиент ── DELETE /api/contacts/{username} ──> Сервер
  Сервер ──> {type: contact_removed} ──> второй клиент (если онлайн)

  Блокировка:
  Клиент ── POST /api/contacts/{username}/block ──> Сервер
  Сервер: помечает в БД, отклоняет relay от заблокированного


9. СЕРВЕРНЫЕ ЧАТЫ (групповые)
------------------------------
  Создание:
  Клиент ── POST /api/chats ──> Сервер ──> {chat_id}

  Вход участника:
  Клиент ── POST /api/chats/{id}/join ──> Сервер
  Сервер ──> {type: member_joined} ──> все участники онлайн

  Сообщение в чат:
  Клиент ── relay_message {chat_id} ──> Сервер
  Сервер ──> relay_message ──> каждый участник онлайн
             сохраняет офлайн-копии для остальных

  Кик:
  Сервер ──> {type: kicked} ──> клиент (если онлайн)
             иначе: при WS-входе в стартовой синхронизации


10. УСТРОЙСТВА / TRUST
-----------------------
  Просмотр:
  Клиент ── GET /api/devices ──> Сервер ──> [{device_id, name, trust_type, level, permissions}]

  Изменение уровня:
  Клиент (creator) ── POST /api/devices/{id}/trust ──> Сервер
  Сервер ──> {type: device_trust} ──> целевой девайс (если онлайн)

  Изменение разрешений:
  Клиент (creator) ── POST /api/devices/{id}/permissions ──> Сервер
  Сервер ──> {type: device_trust} ──> целевой девайс (если онлайн)

  Отзыв:
  Клиент (creator) ── DELETE /api/devices/{id} ──> Сервер
  Сервер ──> {type: revoked} ──> целевой девайс → принудительный logout


11. SUPPORT-ЧАТ
----------------
  Клиент ──> relay_message {type: support} ──> Сервер (сохраняет)
  Клиент ── GET /api/support ──> история
  Саппорт ── POST /api/support/reply ──> Сервер
  Сервер ──> {type: support_reply} ──> клиент (если онлайн)
             иначе: в стартовой синхронизации при WS-входе
