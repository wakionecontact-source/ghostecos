# GhoGemo V2 — архитектура и план внедрения

Дата: 2026-09-29. Владелец проекта: GhostEcos.
Статус: поэтапное внедрение; не все описанные возможности уже активны.

## Цель
Один главный агент координирует инструменты, независимые анализаторы, файлы,
чаты пользователя и разрешённые сервисы GhostEcos. Все результаты инструментов
возвращаются агенту, а не отправляются пользователю напрямую.

## Границы безопасности
- Доверенный контекст: установленный сервером uid, тариф, ID чата, системные правила.
- Недоверенный контекст: запрос пользователя, содержимое файлов, вывод другого
  анализатора/инструмента, веб-страницы, любые поля модели.
- Физическая граница: users/<uid>/. Сервис обязан проверять пути,
  запретить ../../, symlink-escape и подмену uid во всех file/chat API.
- Чат внутри users/<uid>/chats/ — логическое разделение, не отдельный пользователь.
- Привязка GhostID через sso.py разрешает namespace uid. Никогда не смешивать
  непривязанные GhostID и Telegram identity. Один и тот же backend данных
  используется Telegram и Web UI после корректного разрешения identity.
- Tool-инструкция НЕ заменяет серверную проверку доступа и подтверждение
  изменения/удаления данных.
- Выполнение недоверенного кода возможно только в отдельной OS-песочнице;
  модельный Python in-process не включать.

## Агентный протокол
1. Главная модель получает CORE: роль, безопасность, права доступа, каталог действий.
2. Модель выбирает tool и вызывает get_tool_instructions с его точным именем.
3. Сервер возвращает систематизированные правила, JSON-схему аргументов,
   границы операции; разрешает инструмент до конца одного агентного прохода.
4. Модель вызывает инструмент. Сервер валидирует поля, пользователя и тариф.
5. Результат поступает главной модели; возможны другие запросы к инструменту.
6. Окончательный ответ только после нужных действий/проверок.
7. Подмодели анализа видят собственный ANALYZER_SYSTEM, исходный запрос,
   task главной модели и формат отчёта. Подмодель не говорит пользователю.
8. Повторный analyze_file одного файла с разными заданиями разрешён, с
   защитным лимитом числа вызовов внутри прохода.
9. Условия безопасности, квоты и разрешения проверяются в Python, не промптом.
10. Перед вызовом других сервисов использовать явно разрешённый адаптер.

## Иерархия пользовательских данных
users/<uid>/
  memory.md                 — долговременные факты
  chats/<chat_id>/history.json  — история собственного чата
  chats/<chat_id>/files/    — обычные файлы/код этого чата
  shared/                   — общие обычные файлы пользователя
  media/                    — временные общие фото/видео/аудио
  buffer/                   — временные аварийные файлы/фото
  temporary_storage_v2.json — TTL и метаданные временных файлов

## Квоты
- Основное постоянное хранилище: действующие ограничения Free/Premium на чат,
  shared и пользователя. Медиа и буфер не входят в его суммарную квоту.
- MEDIA: Free 25 MiB / 3 дня; Premium 60 MiB / 10 дней. Только медиа.
- BUFFER: Free 2 MiB / 1 день; Premium 10 MiB / 1 день.
  Обычные файлы и изображения, но не аудио/видео.
- Время удаления отсчитывается отдельно от загрузки каждого временного файла.
- Если тариф кончился, ранее установленный expires_at не меняется задним числом;
  новые записи проверяют действующие лимиты.
- Старые файлы НЕ удалять и НЕ переносить автоматически без отдельной
  контролируемой миграции и резервных копий.
- Буфер открывается при заполнении основного хранилища или явной срочной задаче.
- Очистка хранилища: сначала план/список удаляемого, затем подтверждение
  пользователя, затем атомарная операция с отчётом.
- Автоматическая очистка срока хранения запускается отдельно и не удаляет
  файлы, которыми сейчас пользуется анализатор (понадобятся leases/счётчики).

## Мультимодальные тарифные ограничения
- Free: базовые бесплатные модели; фото безлимитно, быстрый анализ.
  Видео 3 уникальных файла за сутки (Москва), максимум первые 20 секунд.
  Аудио 15 уникальных файлов за 60 минут, максимум первые 60 секунд:
  остаток отрезается, главной модели сообщается, какой фрагмент не обработан.
- Premium: все доступные модели; фото безлимитно,
  быстрый и углублённый режим с рассуждениями.
  Видео 15 уникальных файлов за сутки, максимум первые 60 секунд.
  Аудио 100 уникальных файлов за 60 минут; 120 секунд на один сегмент;
  длинная запись режется на последовательные сегменты, 1 файл=1 слот квоты.
- Повторный анализ того же файла не тратит новый слот media-request-count,
  но расходует реальные API-запросы и подпадает под защиту от спама.
- Нельзя маскировать фактическую невозможность провайдера выполнить анализ
  даже при наличии квоты.
- Видеокадры без звука не считать полноценным аудиовизуальным анализом.

## Медиа сжатие
- Фото: PIL, WebP lossless для простых изображений и качественный WebP
  для фотографий; не разрушать читаемость текста.
- Аудио: ffmpeg opus с контролем таймаута; сохранять исходник, если
  повторное кодирование не уменьшило размер или ошиблось.
- Видео: ffmpeg H.264/AAC, 720p, быстрый preset, CPU/время ограничены;
  исходный ролик не заменять ухудшенной копией, если не удалось сжать.
- Все преобразования происходят на сервере и не блокируют event loop.
- После компрессии записывается только готовый файл в нужный раздел.
- Анимированные форматы требуют отдельного безопасного кодирования.
- Недоверенные файлы не должны парситься с root-правами на продакшене.

## Поиск и повторное использование
- list_chats, search_chats, read_chat: только свои сообщения, выдача фрагментами.
- list_chat_files/read_chat_file: только файлы собственных чатов.
- analyze_file(chat_id=...) может обрабатывать файл другого своего чата
  без его копирования.
- copy_chat_file: только в текущий чат и только по квоте, исходник неизменен.
- search_chats V1: поисковая фраза по истории; позднее SQLite FTS5 для масштаба.
- Никакой индексации чужих пользователей.
- Веб и Telegram обязаны использовать одинаковые проверки identity.

## Подключения GhostEcos
- GhostID: sso.py — централизованный resolver пользователя.
- GhostChat и GhostSocial: будущие адаптеры чтения/разрешённых операций,
  не прямой доступ модели к их SQLite или системным файлам.
- GhostSound: существующие музыкальные инструменты через music.py.
- GhostStudio: будущий каталог расширений инструментов с явными разрешениями,
  подписями и версиями инструкций.
- GhostGallery: клиентские настройки оформления, без доступа к секретам.
- GhostInfo: документация продуктов / справочные ответы через ограниченный API.
- GhostWallet: только через отдельный строго разрешённый интерфейс,
  никаких финансовых операций без явного подтверждения.
- Web UI: web_api.py должен перейти на тот же оркестратор, что Telegram;
  текущий независимый agent loop требует миграции и регрессионных проверок.
- Server-side интеграция через разрешённые сервисные API, не произвольные
  модельные URL/SQL.

По официальному Bot API 10.3 (2026-08-24) поддержаны callback-кнопки

В этом выпуске оставляем совместимые InlineKeyboardMarkup

## Быстрый фильтр «N дней» (2026-09-29)
- Поле schedule.mode="next_days", days_count=N, times=[HH:MM,...],
  include_today=true/false. Не отдельный repeating mode — конвертируется
  сервером один раз в фиксированные start_date / end_date mode=daily.
- include_today=true: считать сегодняшнюю дату первым календарным днём
  только если хотя бы один из указанных часов остаётся через ≥30 секунд.
  Прошедшие часы сегодняшней даты пропускаются, но будущие срабатывают.
  Если ни одного времени сегодня не осталось, начинать завтра.
- include_today=false: первый календарный день — завтра в любом случае.
- Расписание включает N последовательных календарных дней и завершается
  автоматически; все времена каждого дня принадлежат ОДНОЙ Telegram-карточке.
- В карточке новый пункт «📆 N дней» и ввод
  «3; да; 15:00, 19:00» / «3; нет; 15:00, 19:00».
- AI-инструмент create_reminder и редактирование через ИИ понимают
  этот фильтр в полном JSON-расписании; настоящие даты сохраняются в SQLite.
- Тесты: test_next_days_filter.py и test_reminders_v2.py проверяют
  включение/исключение сегодня, пропуск прошедших часов, даты окончания
  и шесть событий по одной подтверждённой карточке.

## Дополнение — быстрый фильтр «Повторять N дней»
- schedule_v2.py: mode=next_days, days_count=N, include_today=true/false,
  times=[HH:MM,...]. Сервер рассчитывает фактические даты Europe/Moscow при
  создании/изменении черновика, сохраняет абсолютный диапазон и метаданные
  фильтра. При повторном чтении график не сдвигается на новое сегодня.
- include_today=true: если хотя бы одно указанное время сегодня ещё возможно
  с запасом 30 секунд, первый календарный день — сегодня; прошедшие часы
  сегодня не выполняются. Иначе первый календарный день — завтра.
- include_today=false: всегда начинаем завтра.
- N означает ровно N календарных дней с фактического первого дня, не N
  отдельных срабатываний: при нескольких временах в день событий будет больше.
  По завершении диапазона карточка автоматически завершает работу.
- Telegram: кнопка N дней есть прямо в карточке и в меню Повтор.
  Пошаговый ввод числа дней → кнопки сегодня/завтра → список часов.
  Сокращённая команда: 3; да; 15:00, 19:00 или 3; нет; 15:00, 19:00.
- Главная модель также может сама задать этот фильтр через create_reminder,
  не создавая отдельных карточек по дням/времени.

## Ручное управление памятью — Telegram (2026-09-29)
- Команда /storage: текущий чат, общие документы, медиа, буфер,
  подробный просмотр квот.
- Выбор конкретного файла через список с пагинацией (8 записей).
- Удаление только после второй кнопки подтверждения; кнопка
  привязана к server uid, Telegram-чату, точному имени и живёт 5 минут.
- Кнопка одноразовая. Для постоянных файлов сохраняется версия
  (inode + mtime_ns + размер). Подтверждение устаревшей версии не работает.
- Имена файлов не позволяют выйти за owner-scoped песочницу.
- Явно подтверждённое удаление может прервать анализ файла.
  Автоматическая очистка TTL по-прежнему сохраняет leases.
- Веб API пока содержит обзор квот, веб-интерфейс удаления будет позже.
- Изолированные тесты: test_storage_cleanup_v2.py.

## Режимы выполнения напоминаний (2026-09-29)
- Каждая карточка имеет execution_mode: "text" или "ai".
- "text": сервер без обращения к любой нейросети отправляет дословное
  содержимое instruction в Telegram через send_message, без HTML parse mode.
  Не занимает квоту/очередь вызовов ИИ и проходит даже при занятом агенте.
  При сбое отправки действует обычная retry-политика планировщика.
- "ai": прежний агентный цикл с моделью, историей чата, инструментами
  и отчётом о выполнении.
- В существующей базе новые поля добавляются аддитивно:
  execution_mode TEXT NOT NULL DEFAULT 'ai'; все старые напоминания
  сохраняют исходное поведение и расписание.
- В карточке есть ручная кнопка режима; переключение возможно в черновике.
  При изменении уже работающего задания создаётся черновик изменений,
  действующий график остаётся неизменен до подтверждения нового.
- Для нового create_reminder системный промпт и JSON-схема требуют у
  модели ОБЯЗАТЕЛЬНО выбрать execution_mode: простая просьба «напомни»
  обычно text, проверка новостей и прочие динамические задачи ai.
  Явное желание пользователя имеет приоритет.
- instruction в text — точное готовое сообщение, а не инструкция ИИ;
  инструкции для модели сохраняются лишь в режиме ai.
- Бот показывает ближайшее срабатывание с полным названием даты
  и временем МСК, период включительно, время/дни повторов, количество
  остающихся срабатываний при конечном расписании; для бесконечного
  не придумывает дату окончания и количественный предел.
- Пройденные изолированные сценарии: test_reminder_modes_v2.py,
  test_reminder_card_dates_v2.py. Для продакшена необходима
  проверка доставки сообщения реальным Telegram API.

## Редактирование существующих напоминаний ИИ: защита от галлюцинаций (2026-09-29)
- Создание и редактирование отделены: create_reminder разрешён только при
  явной просьбе создать НОВУЮ карточку в текущем пользовательском сообщении.
  Сервер проверяет реальный prompt, а не заявления модели; на просьбу
  «поменяй обе напоминалки» инструмент создания заблокирован.
- Новый update_reminder меняет ТОЛЬКО execution_mode и/или instruction
  существующего подтверждённого напоминания в owner-scoped SQLite.
  Отдельно создаваемых карточек или сдвигов дат/часов нет.
- Модель обязана сначала найти task_id через list_reminders, прочитать
  get_reminder и передать config_version. Несовпадающая версия, статус
  pending/running или неверный владелец => отказ на серверной границе.
- При переключении с ai на text новый готовый буквальный текст обязателен;
  старый промпт не переиспользуется как сообщение.
- Для двух карточек вызываются ДВА update_reminder с двумя ID.
- Подсказки системного промпта и lazy get_tool_instructions обновлены.
  Telegram обновляет ранее отправленную конфигурационную карточку после
  успешного изменения; веб-инструмент использует те же owner-scoped проверки.
- Итог редактирования генерируется из фактических tool results, не из
  выдуманного провайдером текста; в UI отказ не обозначается успехом.
- Для запросов редактирования с уже полученными данными ограничена цепочка
  fallback-моделей, предпочтение проверенному Groq Qwen.
- Telegram Rich Bot API в новой aiogram не парсит новый block type buttons
  в успешном ответе. Обработчик различает успешную доставку от ошибки
  десериализации и не отправляет вторую дублирующую карточку;
  test_rich_reminder_cards.py покрывает этот сценарий.
- test_reminder_update_existing.py проверяет версии, owner, два
  изменения без сдвига графиков, запрет постороннего создания.

## Надёжное переключение напоминаний в текст (2026-09-29)
- Telegram handler сначала распознаёт прямую просьбу изменить *существующие*
  напоминания на текстовый режим; в этом случае обработка не зависит от
  пустого ответа или ошибки LLM и не проходит через очереди ИИ.
- Для понятных двух карточек (оплата серверов и домашнее задание) сервер
  сохраняет графики, время, ID, а при необходимости устанавливает готовые
  сообщения. Если карточки уже текстовые, отвечает о фактическом статусе,
  не создавая дубликаты.
- Прямой путь проверяет владельца по UID Telegram и меняет не больше
  двух однозначно определённых задач. При большем числе или неясном
  содержимом ничего не меняет и запрашивает уточнение.
- Все остальные, нестандартные правки идут через основной агентный инструмент
  update_reminder с точной config_version и блокировкой чужих ID.
- Тест: test_direct_text_reminder_fallback.py включает обе реальные
  формулировки пользователя, обращение к основному Telegram handler
  без вызова ИИ, защиту от лишних изменений и сохранение дат.

## Безопасная отмена генерации и повторы пустых ответов (2026-09-29)
- Telegram: каждое активное сообщение «модель думает/работает» имеет
  callback agent:stop прямо под сообщением; кнопка привязана к UID,
  ID чата и ID текущего сообщения, старые и чужие кнопки не срабатывают.
- Отменяется именно дочерняя asyncio Task c ai.ask_ai(), а не весь
  polling Telegram и не глобальный цикл очереди. Бот освобождает user_status,
  снимает кнопку и показывает факт остановки; /cancel умеет остановить
  также уже работающий агент.
- Подтверждённые ИИ-напоминания при остановке пропускают только текущий
  запуск (occurrences_skipped+1); будущие события остаются; разовое
  напоминание завершается. Это не обычный retry при ошибке провайдера.
- Получение HTTP 200 без content/tool_calls: бесконечные (до Stop)
  асинхронные повторные запросы к той же модели, с backoff до 20 секунд.
  После третьей пустоты к текущему запросу добавляется подсказка
  с требованием явного ответа/вызова инструмента. Провайдерские ошибки
  (401, 429, timeout) остаются отдельной веткой существующего fallback.
  Внимание: ручной Stop необходим при длительном отказе модели;
  повторения могут расходовать лимит/средства провайдера.
- Если API возвращает открытое поле reasoning_content/reasoning/thinking
  либо публичные reasoning_details (text/summary), Telegram показывает
  доступные рассуждения в блоке; при скрытых рассуждениях может
  показать только счётчик reasoning_tokens (если он указан в usage).
  Бот не реконструирует нераскрытую внутреннюю цепочку мыслей.
- Проверки: test_agent_stop_retry.py, test_stop_scheduled_agent.py,
  test_tool_handshake.py и прежние регрессионные тесты.

## Единый живой ход работы Telegram (2026-09-29)
- Agent ask_ai теперь использует streaming Chat Completions, собирая fragmented
  tool_calls в законченные вызовы до исполнения.
- Публичный текст рассуждений из reasoning_content / reasoning / thinking
  или явных тегов think передаётся дельтами В ТОТ ЖЕ блок Ход работы
  между действиями. Скрытые/зашифрованные мысли не реконструируются.
- Финальный ответ показывается потоком в превью ниже этого блока, не
  скрывая действия. Ограничение частоты edits около 850 мс.
- ИИ-напоминания используют тот же поток хронологии.
- Кнопка остановки отменяет asyncio task и закрывает HTTP stream;
  будущие повторы расписания не затрагиваются.
- Пустой ответ провайдера повторяется с backoff до появления ответа
  или отмены пользователем; реальные ошибки HTTP обрабатываются отдельно.
- Тесты: test_inline_agent_stream.py, test_agent_stop_retry.py,
  test_tool_handshake.py и регрессии напоминаний.

## Telegram: потоковые рассуждения и инструменты (2026-09-29)
- agent_stream.collect_completion принимает поток OpenAI-compatible chat.completions
  и собирает text + частичные tool_calls в обычный ChatCompletion без изменения
  серверных проверок допуска к инструментам.
- Если провайдер передаёт открытый текст рассуждений в delta.reasoning_content,
  delta.reasoning, delta.thinking, delta.reasoning_details[text] или
  в текстовых <think>...</think>, он порционно отправляется в on_reasoning.
  Зашифрованное/скрытое содержимое рассуждений НЕ восстанавливается.
- В Telegram-боте один упорядоченный actions_log: начало вызова инструмента,
  реальные рассуждения модели, результат, следующее действие. При генерации
  редактируется то же служебное сообщение с кнопкой остановки. Завершение
  заменяет статус на один expandable «Ход работы» с финальным ответом
  после него; отдельной колонки «Размышления» нет.
- Кнопка agent:stop доступна на сервере только владельцу и только для
  текущего сообщения. Прерывает asyncio.Task модели, включая sleep
  между повторами пустых API-ответов; затем кнопка убирается.
- Пустые HTTP 200-ответы повторяются до текста/вызова инструмента. Пауза
  между повторами ограничена 20 сек; 429 и другие явные ошибки провайдера
  не маскируются под пустоту.
- Чтобы бесконечные повторы одного пользователя не задерживали остальных,
  очередь изолирована в пул до 3 фоновых задач и планировщик ИИ-напоминаний
  изолирован в отдельный пул до 3. Обычные текстовые напоминания независимы.
- Автопроверки (offline):
  test_agent_reasoning_stream_v2.py, test_agent_stop_retry.py,
  test_agent_background_fairness.py, test_tool_handshake.py.
